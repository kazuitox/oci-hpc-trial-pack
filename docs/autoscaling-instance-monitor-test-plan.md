# 残存インスタンス監視の確認手順

まずは下の5項目を確認する。試験用の関数・応答の書き換え・待ち時間の短縮は使わず、通常設定のまま実施する。

**前提：専用の検証環境で行う。** RM で「管理者へのメール通知を有効化」を選び、管理者メールアドレスを設定・購読承認しておく。コマンドは Controller の `opc` / `ubuntu` で実行する。

## 確認する5項目

| No. | テストするケース | 実行手順 | 想定される状態・動作 | 動作確認の方法 |
| --- | --- | --- | --- | --- |
| 1 | 管理者にメールが届くか | 下記「1」のコマンドで、既存の通知先へテストメールを送る | 指定した管理者にテストメールが届く | 受信箱で件名・本文を確認する |
| 2 | 正常なノードを異常扱いしないか | 通常のジョブを投入し、ノード作成・計算・終了・削除まで進める | 計算中は残存通知が出ず、終了後は通常どおり削除される | Slurm のジョブ状態、OCI のインスタンス状態、メールの有無を確認する |
| 3 | OCI にあるが Slurm にないインスタンスを見つけるか | 下記「3」の試験用 VM を作り、Slurm に登録せず残しておく | 「Slurm に対応するノードがない」という残存通知が届く | OCI に VM があり、Slurm に登録がないことと、メールの対象 OCID を確認する |
| 4 | Slurm と OCI の両方に残った未使用ノードを見つけるか | 検証環境の Autoscaling を一時停止し、非永久クラスターを全ノード IDLE のまま残す | 未使用のクラスターが残っているという通知が届く | 全ノード IDLE・未終了ジョブなし、OCI に残存、メールの対象が一致することを確認する |
| 5 | 残存が解消したことを知らせるか | No.3 の通知を受信した後、試験用 VM を OCI から削除する | 次の正常な監視で解消通知が届く | OCI の終了状態と、件名に `RECOVERED` を含むメールを確認する |

依頼の「作成後に Slurm へ組み込まれず残る」と「Slurm から消えた後も OCI に残る」は、どちらも No.3 の状態になる。ここでは、その状態を検出できるかを確認する。実際の作成・削除処理を故意に失敗させる試験ではない。

## 共通の確認コマンドと待ち時間

現在の検出候補を画面で確認する。

```bash
python3 /opt/oci-hpc/bin/autoscaling_instance_monitor.py --dry-run
```

このコマンドはメールを送らない。候補があれば、対象 OCID と理由が表示される。`{}` は候補なし。エラーになった場合は、メールの判定へ進まず参照エラーを解消する。

メールまで確認するときは、通常実行する。

```bash
python3 /opt/oci-hpc/bin/autoscaling_instance_monitor.py
```

初回は異常を記録するだけで、すぐには送らない。**同じ状態を15分以上残し、もう一度通常実行する。** 定期実行に任せる場合は、初回観測から約15〜20分後に受信を確認する。状態が変わると、待ち時間の数え直しや別の通知が発生する。

同じインスタンス・同じ理由で一度通知済みなら、通常は6時間、同じ通知を再送しない。繰り返し試験する場合は新しい試験用インスタンスを使う。

## 1 メールの疎通を確認する

次のファイルで `topic_id` と `region` を確認する。

```bash
python3 -m json.tool /opt/oci-hpc/conf/autoscaling_instance_monitor.json
```

確認した値を次の `<...>` に入れて実行する。これは Controller の Instance Principal 認証を使用する例。設定の `instance_principal` が `false` の場合は `--auth instance_principal` を外し、既存の OCI CLI 認証を使う。

```bash
oci ons message publish \
  --topic-id '<topic_id の値>' \
  --region '<region の値>' \
  --auth instance_principal \
  --title 'TEST HPC monitor' \
  --body '管理者通知の疎通確認です。障害ではありません。'
```

**合格：** コマンドが成功し、管理者の受信箱に `TEST HPC monitor` が届く。届かなければ、宛先・購読承認・迷惑メール・送信権限を確認する。

## 2 正常な作成と削除を確認する

1. 検証用キューへ、15分以上実行する1ノードのジョブを投入する。
2. Autoscaling でノードが作成され、ジョブが実行されることを確認する。
3. 実行中に dry-run を行い、そのノードが「未使用の残存」と表示されないことを確認する。
4. ジョブ終了後、通常のアイドル削除を待つ。
5. OCI 側で対象が終了し、残存通知も届かないことを確認する。

**合格：** 正常に計算・削除でき、誤った残存通知が届かない。障害や削除失敗が起きた場合は、正常系の試験は未合格とし、原因を確認する。

## 3 Slurm にないインスタンスを残して確認する

本物の計算ノードの登録を壊す代わりに、**監視の所属タグを付けた試験用 VM を1台作り、Slurm には登録しない。** これで「OCI にだけ残っている」状態を作る。

1. No.1 で表示した設定の `deployment_id` を確認する。
2. Controller で、次の空ディレクトリを作る。これは監視が確認するクラスター管理フォルダを用意するためで、Terraform state は置かない。

   ```bash
   mkdir /opt/oci-hpc/autoscaling/clusters/monitor-check-slurm-missing
   ```

3. OCI Console から、設定の `region` / `compartment_id` と同じ場所に小さな試験用 VM を1台作る。専用のホスト名・IP を使い、Slurm の設定や計算ノード用セットアップは行わない。
4. VM に次の freeform タグを付ける。

   | タグ名 | 値 |
   | --- | --- |
   | `oci_hpc_autoscaling_deployment` | 設定の `deployment_id` と同じ値 |
   | `parent_cluster` | `monitor-check-slurm-missing` |

5. VM が RUNNING になったら dry-run を行う。対象 VM の OCID と `SLURM_NODE_MISSING` が表示されることを確認する。
6. 通常実行し、15分以上そのまま残してから再実行する。
7. 管理者メールを確認する。

**合格：** Slurm に登録されていない試験用 VM を検出し、同じ OCID を記載したメールが届く。ディレクトリを用意しない場合は別の理由「管理情報がない」になるため、この試験では先に作る。

## 4 未使用ノードが削除されずに残る場合を確認する

この試験は、**1ノード構成で `permanent=false` の Autoscaling クラスター**を使う。初期計算ノードや永久ノードは使わない。

1. 検証用ジョブでノードを作成し、計算中に検証環境の Autoscaling だけを一時停止する。
2. Controller ユーザーの `crontab -e` で、`autoscale_slurm_disable-resize.sh` を実行する有効な行の先頭に `#` を付ける。元の行を控え、監視の cron は止めない。
3. 試験ジョブを終了させ、対象ノードが IDLE になったことを確認する。新しいジョブは投入しない。
4. dry-run で、対象の `IDLE_CLUSTER_RETAINED` を確認する。
5. 通常実行し、15分以上未使用のまま残してから再実行する。

確認コマンドの `<...>` は試験用の Slurm ノード名に置き換える。

```bash
scontrol show node '<試験ノード名>'
squeue --all --nodes='<試験ノード名>'
```

**合格：** ノードが `State=IDLE`、`CPUAlloc=0`、未終了ジョブなしで OCI に残り、そのノードの残存メールが届く。

**終了後：** `crontab -e` でコメントを外して Autoscaling を戻す。通常の削除処理が進み、OCI に試験ノードが残らないことを確認する。Controller 全体の cron サービスは停止しない。

## 5 解消通知を確認して片付ける

1. No.3 の残存通知を受信した後、その試験用 VM だけを OCI Console で終了する。
2. OCI で TERMINATED になったことを確認する。
3. 監視を通常実行するか、次の定期実行を待つ。
4. 管理者の受信箱で `HPC instance monitor: RECOVERED` を確認する。
5. No.3 で作った空ディレクトリを削除する。

```bash
rmdir /opt/oci-hpc/autoscaling/clusters/monitor-check-slurm-missing
```

**合格：** 前に通知された VM の解消通知が届く。手動で作った VM は通常の Autoscaling 用削除スクリプトに渡さず、OCI Console で片付ける。Boot Volume を残さないことも確認する。

## 追加確認は基本5項目の後に行う

| ケース | 操作 | 想定する結果・確認方法 |
| --- | --- | --- |
| 故障ノードも見つける | 専用の未使用検証ノードを Slurm で DRAIN にし、15分以上残す | dry-run に `SLURM_UNHEALTHY`、その後に対象の通知メール。試験後は元の状態へ戻す |
| 管理情報を失っても見つける | No.3 の VM が残っている間に、空の試験用管理ディレクトリを `rmdir` で消す | dry-run に `LOCAL_RECORD_MISSING`。15分以上続けばその理由で通知 |
| 永久ノードを誤通知しない | 正常な `permanent=true` のノードを IDLE のままにする | アイドル残存の候補・通知が出ない |
| 既存の作成失敗通知も使える | 専用環境でノード作成失敗を再現する | 従来の失敗診断メールが共通宛先に届く |

記録する内容は、**試験番号・対象 OCID・実行時刻・画面の結果・受信メール・合否・後片付けの結果**でよい。認証情報や Terraform state は添付しない。
