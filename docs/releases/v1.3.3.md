# OCI HPC Trial Pack v1.3.3

v1.3.3 は、v1.3.2 に3つの不具合修正を統合したパッチリリースです。Autoscaling の実行ユーザー判定、Slurm の起動順序、topology の Switch 名照合を修正し、監視再同期や構成の失敗、似たキーワードを持つクラスターの混同を防ぎます。

## 実行ユーザーを確認し、監視再同期の失敗を正しく返す

`fix/resize-user-check` を統合しました。`resize.sh` は `USER` 環境変数ではなく、実効 UID と実際のユーザー名で実行者を判定します。`USER` が未設定・空・不一致でも、`ubuntu` / `opc` として実行していれば処理を続けます。root・許可外ユーザー・ユーザー特定失敗時は、副作用のある処理へ進む前に非ゼロで終了します。

監視再同期の失敗は `configure_as.sh` に伝わり、再試行するための構築段階の記録が残ります。`create_cluster.sh` も、root での実行を拒否した際に非ゼロで終了するようにしました。

## SlurmDBD と controller の準備完了を待つ

`fix/slurm-startup-readiness` を統合しました。SlurmDBD が cpu・mem の TRES（Slurm が管理するリソース情報）を正常に返してから slurmctld を起動します。サービスの active 状態に加えて、`scontrol ping` で対象 controller の応答を確認してから後続へ進みます。

同じ `slurm.conf` が残る失敗後の再構成でも、サービス起動と準備確認を行います。HA のバックアップは backup としての応答を確認します。通常版・軽量版の reconfigure は、共有ハンドラで primary の応答を確認してから実行します。

確認コマンドと待機全体には時間上限を設け、失敗が続く場合は理由を返して構成を停止します。既定値と詳細な実行順は [README の起動待機の説明](../../README.md#slurm-の初期起動と再構成の待機)を参照してください。

## Switch 名を完全一致で扱い、検証後に topology を更新する

`fix/autoscaling-exact-keyword` を統合しました。標準版・軽量版・ラック対応版の作成／削除と到達不能ノード回収で、Switch 名を完全一致で照合します。`e5` と `e5-lite` のように一方が他方の先頭部分になるキーワードでも、対象外の一覧を変更しません。

topology 更新を共通の Ansible モジュールへ移し、必要な一覧の欠落・重複・Slurm コマンド失敗時は、書き換える前に停止します。展開・圧縮を検証した後、ロックを保持して原子的に置き換え、既存の権限と対象外の行を保持します。

hostlist の展開・圧縮、および起動確認・reconfigure の子プロセスでは `SLURM_CLUSTERS` を環境から除外します。空文字や別クラスター名の継承による失敗を防ぎ、`SLURM_CONF` と親プロセスの環境は保持します。

## 既存環境では新しいファイルも一緒に配布する

Terraform・IAM・provider、既存の変数名、キュー設定、キーワード、ノード名、クラスター名、設定ファイル形式は変更していません。通常の Autoscaling は、引き続きジョブに応じたクラスター単位の作成・削除です。途中リサイズを通常運用へ追加する変更は含みません。

既存環境への適用は保守時間に行い、進行中の Autoscaling の作成・削除・回収と重ならないようにしてください。

1. v1.3.3 の `bin/resize.sh` と `bin/create_cluster.sh` をコントローラの `/opt/oci-hpc/bin/` へ配布します。
2. `playbooks/roles/slurm/`、`playbooks/roles/destroy_unreachable/` の変更と、`playbooks/library/slurm_topology.py` をまとめて配布します。Slurm role の新しい `files/slurm_readiness.py` と `tasks/` のファイルも必要です。HA ではバックアップ側も同じ配布物を使います。
3. Slurm の構成を反映する場合は、通常の `/opt/oci-hpc/bin/configure.sh` を再実行します。設定変更の経路ではサービスを再起動するため、稼働中ジョブへの影響を確認してから実施してください。
4. `ubuntu` / `opc` として監視再同期を行い、Slurm の応答と対象クラスターの topology 更新を確認します。詳細は [README](../../README.md#手動クラスター操作)と[調査・更新手順](../autoscaling-topology-identity.md)を参照してください。

リリース公開や Resource Manager の構成ファイルの差し替えだけでは、既存コントローラのファイルは更新されません。切り戻す際も、新旧のタスクと共通モジュールが混在しないように配布物をそろえます。既に壊れた topology の自動修復や、Slurm の DB・状態ファイルの初期化は行いません。

## 検証結果と確認範囲

3つの修正を統合した `master` のローカル全件テストは、543件、失敗0件、スキップ3件でした。Shell 構文検査、変更した YAML 15ファイルの解析、待機・作成・削除・回収タスクの Ansible 構文検査も成功しています。

スキップは、Terraform CLI が必要な2件と、`ANSIBLE_PLAYBOOK_BINARY` の指定が必要な HT role の検証です。既存のサーバータスク全体の Ansible 構文検査は、検証環境に `mysql_db` モジュールがなく完了していません。Slurm 起動待機と topology 更新の回帰テストでは、Ansible とコマンドのスタブを使った処理検証を行っています。

2026-10-05 に利用者から、統合後の動作確認が完了したとの報告を受けています。確認した OS・構成・操作の詳細は未記録のため、この報告を HA・ラック対応・到達不能ノード回収など全構成の検証完了として扱いません。追加確認の手順は [回帰確認台帳](../REGRESSION_LEDGER.md)の REG-021 / REG-022 / REG-023 を参照してください。
